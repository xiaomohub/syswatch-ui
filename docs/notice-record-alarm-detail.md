# 通知记录：告警摘要与详细内容（后端开发说明）

本文只说明 **`noticeRecordList` 单条里的告警文案**：为什么常见叫「摘要」、和「详细」怎么分工、后端怎么实现最省事。  
统一响应信封、路径前缀等与故障中心一致（`/api/w8t/notice/...`）。

---

## 1. 为什么界面里叫「告警摘要」

- **列表场景**：分页接口不宜每条带几万字，字段名上往往用「摘要」表示「这条通知对应的人读文案」（可能是一整段，也可能是截断后的短段）。
- **渠道侧**：飞书/邮件实际发出的也常是一段合并后的说明，落库时通常就记这一条字符串。

因此：**「摘要」不等于一定比某处「详细」更短**；它只是「通知记录里承载告警说明的主字段」的习惯叫法。  
**若你落库的就是完整正文**，那对前端来说「摘要」里已经是全部信息，没有第二份隐藏详情。

---

## 2. 用户要看「更具体、更详细」时，后端可以怎么做

按你们数据是否截断，选一种即可。

### 方案 A：不截断 —— 只用一个字段 `alarmMsg`（最简单）

- 列表里 `alarmMsg` 存 **完整 UTF-8 纯文本**（可含换行）。
- 列表接口若担心体积：可以 **限制单条最大长度** 或 **分页减小 `size`**，而不是把字段语义改成「只有摘要」。
- **前端**：通知记录页「查看」弹层展示的是 **`alarmMsg` 全文**（与列表是否截断展示无关）。

### 方案 B：列表必须短 —— 同一条记录再加一个「全文」字段（推荐）

| 字段 | 类型 | 说明 |
|------|------|------|
| `alarmMsg` | string | 列表展示用：短标题/首段/截断后的说明 |
| `alarmDetail` | string | **完整正文**；与 `alarmMsg` 同时返回时，弹层应优先展示本字段 |

结构化明细（序列列表、labels 等）如需一并给前端，可用 **`alarmDetail` 为 JSON 字符串**，或另加 **`alarmPayload`（object）**，与可读正文分离。

### 方案 C：详情在告警/事件中心 —— 记录里只带关联键

- `alarmMsg` 仍为人读的简短说明。
- 同条带 **`eventId`（已有）**，必要时加 **`ruleId`**；完整时间线、原始指标、多序列等走 **现有事件/告警详情接口**，通知记录不负责承载大块数据。

### 方案 D：单独详情接口

- 列表极轻，仅 `eventId` + `alarmMsg` 摘要；完整事件走 **`GET /api/w8t/notice/noticeRecordAlarmDetail`**（契约见 **`docs/notice-record-alarm-detail-api.md`**）。

---

## 3. 和当前前端的对应关系

- 弹层优先展示：**若存在非空 `alarmDetail`，用 `alarmDetail`；否则用 `alarmMsg`**（见 `NoticeRecords.vue`）。
- 失败原因仍用字段 **`errMsg`**，与告警正文无关。

---

## 4. 小结（给后端排期用一句话）

**要么 `alarmMsg` 就是全文（方案 A），要么在列表项里增加 `alarmDetail` 存全文（方案 B），要么明确详情走事件接口/独立详情接口（方案 C/D）。** 避免只截断 `alarmMsg` 又不提供任一「全文」出处，否则前端无法凭空还原详细内容。
